## Quality and planning (quality-bootstrap; details in docs/quality/toolchain.md)

- Gates: `<gate command>`. Run them before claiming work is done and quote the result.
- Deciding and asking: agents have the tools to make every decision, so they make them. Research each decision that shapes the result — the repo's docs, DECISIONS.md and ADRs as input, not authority; current best practice and industry standards on the web; any installed skill or agent that covers its domain — then take the best option, even over a logged decision or ADR (log a superseding entry; supersede the ADR), and log the non-obvious ones in DECISIONS.md. Ask (AskUserQuestion: what you found, the options with their evidence, your recommendation first) only (1) an opinionated question: a product decision that is costly to reverse with no clear winner after research, or (2) for what only a human may do or authorize: an irreversible or security-sensitive action, a change outside the run's worktree that its steps do not prescribe, a test that looks wrong outside a planned change. Never end a run to get input: ask, wait, continue.
- Tests are the spec. Never weaken, delete or rewrite a test or the test infrastructure to make code pass. Test changes that a plan task names with its reason (new cases, updated tables, un-skipped suites, rig, fixture or seeding fixes the change requires) are planned work: the planner and the readiness review decide them and log them in DECISIONS.md, without asking. Ask the user with AskUserQuestion — what, why, evidence, your recommendation — only when, outside any planned change, an existing test or the test infrastructure looks wrong; then continue with the answer. Never stop the run for it; write `BLOCKED.md` (what, why, evidence) only when the user chooses to stop.
- Gate scripts, gate configs, baselines and `.claude/settings.json` change only in human-reviewed commits.
- Use only the tools in docs/quality/toolchain.md; a new tool needs a policy and catalog update first.
- Plans: ground them in the existing code with the feature-dev `code-explorer` agent (closest implementation, its wiring, the conventions).
- Acceptance criteria are EARS with ids (`AC-<n>: WHEN … THE system SHALL …`); every task names its AC ids and an automated verify command.
- A new interface between modules: follow docs/quality/interface-design.md (codebase-design, scored with api-and-interface-design) and record an ADR before tasks build on it.
- At most ~10 tasks per plan; split bigger work into vertical slices.
- Execute a plan only after `plan-readiness` returns PASS (CONCERNS need the owner's OK). Plans and DECISIONS.md live in `<plans directory>`.
